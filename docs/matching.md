# 与 OCS 的适配细节

这份文档记录「为什么要这么改」。日常使用看 [README](../README.md) 就够了，
只有你想改答题逻辑、缓存行为，或者怀疑某类题处理得不对时，才需要读这里。

所有结论都来自 OCS 源码，不是猜的。涉及的文件：

- `packages/core/src/core/worker/utils.ts` —— `splitAnswer()`，答案分隔符
- `packages/core/src/core/worker/resolvers/single.ts` —— `resolveSingle()`，单选四阶段匹配
- `packages/core/src/core/worker/resolvers/multiple.ts` —— `resolveMultiple()`，多选匹配
- `packages/core/src/core/worker/resolvers/judgement.ts` —— `resolveJudgement()`，判断题
- `packages/core/src/core/answer-wrapper/answer.wrapper.handler.ts` —— 题库配置字段

## 1. 答案对齐：避免「选项长得不一样」被跳过

OCS 拿到答案后不是直接采用，而是要过一道四阶段匹配（`resolvers/single.ts`）：

| 阶段 | 规则 |
|---|---|
| 1 | 归一化后 `答案 === 选项`，或 **`答案.includes(选项)`** |
| 2 | Dice 相似度 **> 0.6** |
| 3 | 答案是单个 `A`/`B`/`C` 字母 |
| 4 | 多片段合并后重试 |

注意阶段 1 的方向是「**答案包含选项**」。所以当选项是「爱因斯坦的相对论」而模型答「相对论」时，
方向相反，相似度仅约 0.33，**OCS 会直接丢弃这道题**——这就是"答案和选项长得不一样就跳过"的原因。

服务端因此有 `matching.align_one()`，把模型答案改造成 OCS 认得的形态：

1. 原文相等（含 `#`、`//` 这类符号答案）→ 返回该选项原文
2. 归一化后相等 → 返回该选项原文
3. 答案是某选项的子串且**只命中一个** → 返回该选项原文
4. 相似度 > 0.6 → 返回该选项原文
5. 都不满足 → **返回 `None`，调用方把这一段丢掉**

同时在 prompt 里明确要求"**答案必须是选项原文照抄，禁止同义改写或概括**"。

### 为什么「对不上就丢掉」比「凑一个」好

原来第 5 步是「取相似度最高的选项」，保证总能返回点东西。模型答偏的时候，
这一级就会把一个**错误**的选项交给 OCS 点下去。多选题尤其明显：几段答案被兜底到
同一个选项，OCS 点两下（选中又取消），页面上的勾和答题面板的状态就对不上了——
用户看到的就是「明明都选了，面板还显示未选」。

改完之后：对不上的段直接丢。少点一项只是没答全，点错一项会把对的也带偏。

多选还多一步：模型不用 `#` 分段、把几个正确选项抄成一句话时，
`matching.options_in_text()` 会把这句话里包含的选项原文挑出来，逐个还原。

## 2. 答案里不能出现 `#`、`|`、`;`、`；`

OCS 的 `splitAnswer` 默认分隔符是：

```js
['===', '#', '---', '###', '|', ';', '；']
```

答案里出现其中任何一个，都会被切成多段。最典型的一道题：

> 在 Python 中，用于表示单行注释的符号是？

正确答案就是 `#`。但 `"#".split("#")` 得到两个空串，过滤后是空数组，
OCS 判定这道题没答上，页面显示「无法选择」。

现在的处理：`llm._is_separator_only()` 认出这种"整个答案就是分隔符"的情况，
改用**选项标号**返回（如 `A`），走 OCS 阶段 3 的纯字母兜底。
选项正文外面包的反引号、引号也会先剥掉再比对（`matching.trim_wrap()`），
所以 ``A. `#` `` 这种写法也能命中。

## 3. 多选答案去重

OCS 答多选题是「逐个点选项」：拿到 `甲#乙#丙` 就点甲、点乙、点丙。
如果同一段出现两次，它会把同一个选项点两下——第一次选中，第二次取消选中，
状态对不上，页面就卡在「等待顺序答题中」不再往下走。

这种重复是在**对齐之后**才出现的：模型给的两个不同表述被对齐到同一个选项。
所以去重放在对齐之后做（`llm.dedupe_parts()`）：

```
模型输出  甲#甲#乙#乙#丙
对齐后    甲#甲#乙#乙#丙
去重后    甲#乙#丙          ← 送给 OCS 的最终答案
```

**只对多选题去重**。填空题的多空答案允许相同（两个空都填「人民」是合法的），
去重会把第二个空的答案吃掉，所以 `completion` 不经过这一步。

## 4. 判断题必须返回「正确」或「错误」

OCS 判判断题不看选项文本，只看答案里有没有「对/错」类词（`resolvers/judgement.ts`）：

```ts
const answerShowCorrect   = answers.find((a) => matches(a, CORRECT_WORDS));
const answerShowIncorrect = answers.find((a) => matches(a, INCORRECT_WORDS));
if (answerShowCorrect || answerShowIncorrect) { ...返回对应选项... }
return { finish: false };        // ← 落到这里，页面显示「无法选择」
```

`matches()` 是**精确相等**，不是包含。所以答案写成选项标号 `B` 是无效的——
`"B"` 不等于任何一个正确/错误词，OCS 认为这道题没答上，选项保持空白。

服务端因此有 `llm.normalize_judgement()`：

1. 答案里有词 -> 直接用（**先判「否」再判「是」**，否则「不正确」会被「正确」抢走）
2. 只有标号（`B`、`选B`、`B.`）-> 取出该选项的正文，再判一次
3. 与某个选项正文相同 -> 判该选项
4. 都判不出来 -> 原样返回，宁可让 OCS 跳过也不瞎猜

第 2 步必须按选项正文判断，不能假设 A=对、B=错——选项顺序有可能是反的。

## 5. 简答题不能用 `#` 分段

OCS 见到 `#` 就当「多个空」，进入顺序填写模式，挨个找输入框往里填。
简答题页面通常只有一两个输入框，填到第二段就找不到了，**这道题卡住不动**，
后面排队的题目全部显示「等待顺序答题中」，看起来像一道都没答上。

所以 `llm.ask()` 最后有一道判断（`should_split()`）：

| 题型 / 题面 | 答案格式 |
|---|---|
| 多选 | `#` 分段（OCS 的硬要求） |
| 填空题且题面 ≥2 个空位 | `#` 分段，**且段数必须等于空位数** |
| 其余（简答、单空填空） | 顿号或逗号连成一段 |

注意**空位数只在下划线里数**（填空题另算括号，见下）——括号在多选题题干里太常见
（「……包括（）」），拿它当空位会把多选题误判成填空。

### 多空填空：段数必须正好等于空位数

这是踩得最狠的一处。OCS 的 `resolveCompletion`（`resolvers/completion.ts`）：

```ts
if (ans.length !== 0 && (ans.length === blankCount || blankCount === 1)) {
	if (ans.length === blankCount) return { finish: true, answers: ans };
	else if (blankCount === 1) return { finish: true, answers: [ans.join(' ')] };
}
return { finish: false };
```

`blankCount` 是页面上输入框的个数（`options.length`），`ans` 是答案经 `splitAnswer`
切出来的段数。**段数不等于输入框个数，直接 `finish: false`——一个空都不填**。
不是「填不满」，是完全不动，页面上看着像没反应。

所以两个空的题交一整串 `and or`，等于没答。而 `splitAnswer` 只认
`['===', '#', '---', '###', '|', ';', '；']`，顿号、逗号、空格**都不是**分隔符。

改之前有四层叠加在这个结果上：

| 位置 | 原来的行为 | 后果 |
|---|---|---|
| `build_prompt()` | 只说「多个空用 # 连接」，没给空位数 | 模型不知道有几个空，把两个答案连成一句 |
| `clean()` 填空分支 | 无条件 `splitlines()[0]` | 模型分行写 `and\nor`，第二个空被整段丢掉 |
| `should_split()` | 第一句就是 `if "#" not in ans: return False` | 题面明明 2 个空，也判成「不用分段」 |
| `join_as_text()` | 没有 `#` 就原样返回 | 最终交出一整串，段数 1 |

现在三处一起补：

1. `blank_count(title, qtype)`：先数 `____`；一个都没有、题型又是填空时，再数 `（ ）`。
   括号只在填空题里算数，选择题不受影响。
2. `build_prompt()` 把空位数写进 prompt：「这道题有 2 个空……用 # 连接，不要写序号」。
3. `_fit_blanks(ans, n)` 兜底：依次用 `#|;；` → 换行 → `、,，/` → 空格切，
   取第一个能切出**正好 n 段**的结果；切多了取前 n 段；都切不出来就原样返回。
   段首的 `1.`、`(1)`、`①`、`A.` 会先剥掉。

「空格」排在最后：`and or` 只能靠它分开，但含空格的中文长短语被误切的风险也最大，
能不用就不用。

`should_split()` 的判断顺序同时反过来——**先看题面有几个空，再看答案**：

```python
def should_split(title, qtype, ans):
    if qtype == "multiple":
        return True
    if qtype == "completion" and blank_count(title, qtype) >= 2:
        return True
    return False
```

顺带一个安全边界，决定了这个方向可以放心偏：页面上只有 1 个输入框时，
OCS 有 `blankCount === 1` 分支，会把多段用空格拼起来。所以**多分段不会伤到单空题**；
反过来，单段喂给多空题必然全失败。永远往「按题面空位数分段」偏。

另外 `detector.py` 对 `completion` 的格式检查也放宽了：原来要求题面必须以
`___`/`。`/`？` 收尾，「简述新民主主义革命的三大法宝及其相互关系」这种
既没空位也没标点的题会被当成非题目直接跳过，连答题机会都没有。
现在「简述/论述/试述/请/如何/怎样…」开头也算合法题面。

## 6. 简答题要有内容：单独一套 prompt

简答题原来和选择题共用一份 prompt，而那份第 2 条写死「只输出答案本身，
不要任何解释」，模型严格执行，简答就只剩关键词：

| 题目 | 改之前 | 改之后 |
|---|---|---|
| 简述新民主主义革命的三大法宝及其相互关系 | `统一战线、武装斗争、党的建设`（14 字，**相互关系没答**） | 187 字，三个法宝 + 三者关系的完整论述 |
| 请简述 Python 中列表和元组的区别 | `列表可变，元组不可变`（10 字） | 四方面区别（可变性/语法/性能/用途）+ 字典键的补充 |

现在 `detector.is_short_answer()` 先把简答从填空里分出来
（必须是 `completion`、题面无 `____` 空位、且带「简述/说明/区别/关系/如何…」这类措辞），
再分两套走：

| | 选择题 / 判断 / 填空 | 简答 / 论述 |
|---|---|---|
| prompt | `SYSTEM_PROMPT` | `SYSTEM_PROMPT_LONG` |
| max_tokens | 512 | 800 |
| 清洗 | 取首行、把 `;` `\|` 统一成 `#` | 多行**全部保留**并合并成一段 |
| 选项对齐 | 走 `align_one` | 不参与 |
| 分隔符 | 多选必须用 `#` | `#` 换成全角 `＃`，`；` 换成句号 |

**「取首行」这个坑值得单独记一笔**：原来 `clean()` 里有一句无条件的
`ans.splitlines()[0]`，模型分三行写的简答只有第一行活下来。
这是"简答答得太简单"最直接的元凶，比 prompt 的影响还大。

还有一句也删了：

```python
if "#" in ans:
    ans = re.sub(r"\s*[;；,，]\s*", "#", ans)   # 逗号变 #
```

它只看答案里有没有 `#`，有就把**全篇中文逗号**换成 `#`，再由 `join_as_text`
补成顿号，产出「我们必须坚持而不能离开社会主义、第二、我国的……」这种病句。
现在只有选择题才会做分隔符归一化。

## 7. 非题目拦截：避免把 PPT 正文当题目搜

OCS 的 `buildAnswererEnv` 里有这么一句：

```ts
const env = { type: ..., title: params.title, options };
```

**标题文本原样透传，不做任何过滤**。所以课件页/说明页上选择器抓到的 PPT 正文，
会被整段传给题库，服务端只能对着大段课件问模型，既浪费额度又答非所问。

服务端加了 `detector.looks_like_question()` 提前拦截，命中则返回 `code=0`
（OCS 会回退其他题库）。判定分三档，越往后判据越弱、规则越严：

| 档位 | 情况 | 规则 |
|---|---|---|
| 一档 | 带了 ≥2 个选项（单选/多选/判断） | 只看长度 ≤200 字、行数 ≤6 行，**关键词黑名单完全不生效** |
| 二档 | 填空题 / 简答题 | 有空位（`____`）、或以标点收尾、或以「简述/论述/请…」开头，满足其一即放行 |
| 三档 | 无选项的其他情况（课件标题、说明文字） | 长度 ≤120 字、行数 ≤3、不命中课件关键词 |

**一档为什么不再看关键词**：真题题干里出现「总结」「概述」「首先」「学校」「专业」
这类词太常见。曾有真题「毛泽东在《〈共产党人〉发刊词》中总结的……三大法宝包括（）」
带了完整的四个选项，却因为一个「总结」被一票否决，OCS 显示「本地AI题库 共 0 个结果」。
带了 A/B/C/D 的文本基本只可能是题目，PPT 正文不会给自己编四个选项。

反过来，PPT 的栏目标题（「本章小结」「概述」）没有选项，自然落到三档被拦下。

控制台的「**非题目跳过**」计数就是这一层拦下来的数量。

> OCS 侧的元素选择器行为无法从服务端改变，这里是在服务端兜底。
> 如果仍有漏网，把被抓到的文本特征补充进 `_NON_QUESTION_HINTS` 即可。

## 8. 缓存管理与「不缓存题目」开关

### 开关为什么是「读和写都跳过」

`NO_CACHE` 为真时，`service._handle()` 里 `cache_get` 和 `cache_put` **两处都跳过**。

只停写是不够的。库里已经存着的答案照样会命中，用户开了开关却发现拿到的还是旧答案，
第一反应是开关坏了。要真的每次都重新问模型，读取这一侧也得绕开。

状态写在 `.env` 的 `NO_CACHE`，重启保留。网页上拨开关走 `POST /api/config`
的 `no_cache` 字段，`save_config()` 写完 `.env` 同时改内存变量，立即生效不用重启。

判断有没有传这个字段要用 `"no_cache" in data`，不能靠真假值——传 `false` 和没传
在 Python 里都是假值，分不出来就会出现「关了开关但没关掉」。

### 删除按 qhash，不按题干

`qhash` 是主键，一题一个。题干不能当删除条件：里面可能有引号、换行，
而且同一段题干在不同选项组合下算不同的题，容易删错或删不干净。

列表接口因此要把 `qhash` 一起返回。前端把它放进删除按钮的 `onclick` 里传回来。

### 清空只删 answers 表

`stats` 里的累计查询、调用次数、失败次数是历史事实，清缓存不代表之前没查过题。
一起抹掉，后面排查「服务有没有收到请求」就失去依据了。

### 三个接口

| 接口 | 参数 | 说明 |
|---|---|---|
| `GET /api/cache` | `q`、`sort`、`unused`、`limit` | 列出缓存，返回 `qhash` / `title` / `answer` / `hits` / `updated`，外加 `total` 和 `all_total` |
| `POST /api/cache/delete` | `{"hash": "..."}` | 删一条，返回 `deleted` 条数（0 表示本来就没有） |
| `POST /api/cache/clear` | 无 | 清空，返回 `deleted` 条数 |

用 POST 不用 DELETE，和现有的 `/api/config` 保持同一种风格。

### 排序和筛选

三种排序，`sort` 参数取值：

| 值 | 排序 | 用途 |
|---|---|---|
| `updated` | 最近更新倒序（默认） | 刚答的题在最上面 |
| `hits` | 命中次数倒序 | 找出反复出现的题，这类答错影响最大 |
| `short` | 题干长度升序 | **排查工具**：排出来一串十几个字的答案，多半是模型答得敷衍或被截断 |

`unused=1` 是筛选，只看 `hits = 0` 的题——存下来却从来没被第二道题命中过，
要么是课件误抓，要么答案有问题，配合清理正好用。

实测一门课的 49 条缓存里有 46 条命中次数为 0。一门课里重复的题本来就少，
所以这个筛选值钱，`hits` 排序反而用不太上。

**排序字段必须是白名单**。SQL 的 `ORDER BY` 后面没法用参数占位符，
只能把前端传的字符串拼进语句，不校验就是注入口子。所以 `store._SORTS`
做成字典，认不出来的值一律回落到 `updated`。

另外 `all_total` 要单独返回：`total` 是过滤后的条数，清空按钮要知道全库有多少条，
拿 `total` 当全库数，一搜索就会显示错。

### 前端为什么单独做一页

统计、最近请求、缓存列表原本挤在一屏，刷课的时候根本看不过来；
删除又是不可逆操作，和统计混在一起容易误点。所以主页只留一个入口按钮和一个开关，
列表、搜索、删除都搬到 `/cache.html`。

主页那个开关在轮询里只在首屏同步一次（`if (!full && filled) return;` 之后才赋值），
否则每 5 秒的刷新会把用户刚拨的开关冲回去。
